# Changelog

All notable changes to PyAPS are documented here. The format follows
[Keep a Changelog](https://keepachangelog.com/en/1.1.0/) and versions follow
[Semantic Versioning](https://semver.org/) (`MAJOR.MINOR`, patch releases as `MAJOR.MINOR.PATCH`).

## Unreleased

### Changed (IFU Galactic mode: the FERRE metallicity columns `FEH_FERRE` / `FEH_ERR_FERRE` renamed `MH_FERRE` / `MH_ERR_FERRE`, 2026-11-16; doc/aps_ferre.md section 12)
- **Same reason and rule as the MOS rename of 2026-11-12 (Thomas Hajnik, aps_ferre 2.1):** the FERRE grid dimension METALS is the overall metallicity [M/H], not [Fe/H]. `aps_ifu_ferre` (1.2) writes `MH_FERRE` / `MH_ERR_FERRE` in `FERRE_IFU_TABLE` of `<head>_P####_FERRE.fits` and, through `aps_L2merge.ifuGalL2merge` (generic, by column name), in the IFU Gal L2 `STAR_TABLE`. Values, units (`dex`), the white-dwarf marker (-10) and the column position are unchanged; the header card `APS_FR_V` (= `__aps_ferre_version__`, 2.1) is now also written to the IFU FERRE table, a file without it has the old names. `FEH_RVS` / `FEH_ERR_RVS` (RVSPECFIT, really [Fe/H]) keep their names.
- **Readers accept both names, so old IFU L2 files keep working:** `aps_IFUviewer` (`_ferre_mh_col`: map option `FERRE_MH`, a saved `FERRE_FEH` map type is the same column, FERRE fit panel title `[M/H]`), `apsPlot.spaxel_map` colour rule.
- **Not affected (checked):** the IFU L2 templates in `doc/L2_templates` have no FERRE columns (IFU_ExGal templates; the Galactic-mode STAR_TABLE has no template); FESWI reads only the MOS `ferre_<head>.fits`; `aps_L2merge` joins by `BIN_ID` and copies whatever columns exist. WEAVE-ICD-027 v8.00 still lists `FEH`.
- Test: `tests/test_ifu_ferre_mh_columns.py`.

### Added (IFU_PR `seg2d_deblend_mode`: blends of stars in a crowded field are split, nothing else changes; OB 14699 of night 20260315, 2026-11-13; doc/aps_ifu_seg2d_robust.md section 7)
- **The problem.** In OB 14699 (globular cluster M3) the coarse deblending (`seg2d_deblend_nthresh` 4) left 15 of 44 detections as blends of 2 to 13 stars (the largest a chain of 8 stars, a = 12 arcsec); each blend is one IFU patch and the Galactic stage bins it and runs FERRE on every bin.
- **New parameter `seg2d_deblend_mode`**: `fixed` = exactly the previous behaviour; `auto` (default) = the same extraction, then, only in a crowded field (>= 10 compact point-like detections), a parent is replaced by its children when two or more of them are real sources (>= 7 % of the flux, prominence >= 10 % of their peak and >= 6 sigma, peaks >= 1.5 x PSF apart), the parent is not extended (a galaxy breaks into dozens of fragments and keeps whatever touches it whole), every child is point-like, none holds more than 70 % of the flux, and the split saves at least 10 Galactic-stage bins and 15 %. A detection that fails any rule is kept exactly as sep returned it, and when nothing is split the arrays are returned untouched (bit for bit the `fixed` result). Children get their own `a`, `b`, `theta`, `x`, `y`, `flux`, `npix`, ... (sep's formulas) and their own `A_world` / `B_world`; the segmentation map is relabelled consistently. `seg2d_max_targets` is applied after the split and a split never goes over it.
- **Plumbing**: `--seg2d_deblend_mode` (`aps_ifu_prepare.py`, `ifu_worker_prepare`, `ifu_seg2d`), `aps_runner.py` (JSON > YAML > `auto`), the shipped LIFU / MIFU `IFU_params` JSON, `script_params.yaml.example`, `doc/aps_ifu_prepare.md`. **To turn it off: `"seg2d_deblend_mode": "fixed"`.** `<head>_seg2d_summary.json` and the `SEG2D_SUMMARY` line say the mode, `n_parents`, `n_parents_split`, `n_children` and (auto) the gate, PSF size, reasons parents were kept whole and the list of splits. Any exception in the step is caught: the normal extraction is used and a WARNING is printed. New module `py/PyAPS/aps_ifu_deblend.py`.
- **Real data** (Imperial pod, read-only, thresholds of each OB): OB 14699 44 -> 49 detections, largest a 12.0 -> 5.0 arcsec, estimated Galactic-stage bins 494 -> 412. Of all 108 different finished white-light images, 107 give exactly the same detections and segmentation map in both modes (44 pass the gate, among them the fields with the largest galaxies); OB 14699 is the only one that changes. Not decidable from the collapsed image (fibres of 2.6 arcsec): a compact galaxy with two knots looks like two stars; the rules are deliberately strict, and a galaxy-only survey can set `fixed`.
- Tests: `tests/test_seg2d_deblend.py` (24: chain split into the stars with the right positions; sparse field, isolated galaxy with knots, galaxy with knots in a crowded field untouched; crowded field with a galaxy; cap; `fixed` pinned against the old code path; sep's columns; summary; wiring; OB 14699 where `PYAPS_TEST_DATA` has it); `tests/test_aps_common_args.py` (the new flag).

### Fixed (IFU_ExGal: the serial path `--mp_ExGal 1` and the pool gave different emission lines, because FITS arrays are big-endian and a pickle makes them native; `aps_native.py`, doc/fits_byte_order.md, 2026-11-15)
- **Symptom** (from the investigation of 2026-11-14): OB 26140 patch 3 (LR, 21 bins) run with 1 and with 2 workers differed in one bin only, the last: its emission-line FLUX / AMPL / AON / V / SIGMA / FORM_ERR in `emippxf.fits`, `emippxf_BIN`, `emippxf_lines_BIN`, `emippxf_spec_BIN`, the cleaned spectrum and the line strengths derived from it (the strongest lines by 1e-6 to 1e-4, weak lines of that bin by tens of per cent: `[FeVII]` 5720 amplitude 45 %, the formal velocity error of the Balmer lines a factor 3). Each path was exactly repeatable, so it was not the Monte-Carlo noise.
- **Cause.** FITS tables are big-endian and astropy returns them that way (`>f8`). `np.array(hdu[1].data.SPEC.T)` keeps the byte order, so the serial loop handed `bin_data[:, i]` and `noise[:, i]` to the fits as big-endian strided views. A `multiprocessing` queue pickles every job and a pickled non-contiguous slice comes out native, so a pool worker fitted native `float64`. The two byte orders of the same numbers are not computed the same way: numpy reduces byte-swapped data through its buffered cast in chunks of 8192 values and native contiguous data in one pairwise pass, so a sum of 8000 to 10000 pixels differs in the last digit (8 of the 21 bins: `np.sum` of the good pixels; `np.std`, which sets the regularisation `bias` of the stellar re-fit, in exactly one: bin 20, 5.7e-14). The stellar re-fit of bin 20 then moved by 1e-10 (the ill-conditioned fit amplifies it; bins 0 to 19 are bit for bit the same either way) and the emission fit that subtracts that stellar model by up to the sizes above. Shown in one process by fitting the same bin with `>f8` and with native copies (only bin 20 differs), and by logging the arguments of `run_ppxf_emi` in both modes: they differ in dtype (`>f8` against `float64`) and, for bin 20 only, in `stellar_bestfit`. Not BLAS threads (excluded 2026-11-15), not the shared inputs, not the seed.
- **Fix.** `py/PyAPS/aps_native.py` (`native_array`, `is_native`): the spectra, errors and stellar model that IFU_ExGal fits are made native where they are read (`IFUExGalPPXF` SPEC / ESPEC, `IFUExGalEMIPPXF` SPEC / ESPEC / MODEL_PPXF), same values, same memory order, still a copy. A serial loop, a pool worker and a lane now fit the same bytes.
- **Checked on real data** (OB 26140 patch 3, ARCUS pod, scratch, `PYAPS_PATCH_SEED=7`, all 17 products compared column by column without the random `ERR_*` columns): after the change serial = 2 workers = 3 workers (0 differing columns in 17 files); 2 and 3 workers before against after: 0 differing columns, so **the production (pool) path is unchanged to the bit**; only the serial path changed, to the pool result. This settles the "within 7.5e-4 relative for another patch" remark of the serial-path entry of 2026-11-13.
- Tests: `tests/test_native_byte_order.py` (7: value-for-value conversion, native input stays a copy, memory order kept, what a worker receives equals what the serial loop sees, reductions agree, the two stages read through the helper).
- **Not changed, same pattern** (listed in doc/fits_byte_order.md): the MOS stages read their spectra the same way (`MOSExGalPPXF`, `MOSExGalPrepare`, `MOSExGalEMIPPXF`, `MOSExGalLS`) and have a serial branch; the parent-only reader `IFUExGalPrepare.loadAllSpectra` (Voronoi binning) was left because a change there could move a bin edge. Neither was run end to end here; take the same step with an A/B like the one above.

### Changed (IFU_ExGal: the width of each patch is set when its bins are known, 2026-11-14; aps_ifu_patch_pool.py `WidthBroker`)
- **Why**: the lane plan from the area of the apertures cannot work for ExGal. Voronoi bins follow the S/N, not the area (384 patches of 29 OBs on Imperial: area 3974 arcsec^2 -> 2 bins, 4035 -> 505, 6908 -> 606, 12154 -> 3326). OB 26037 (one patch of 606 bins, ten of 2) therefore ran one patch after the other, 53 min on 24 CPUs; the uneven lanes of the entry below only help when the estimate is right (they stay for IFU_Gal, where bins do follow the area: 420 predicted, 495 measured).
- **What**: `plan_workers(..., dynamic=True)` (IFU_ExGal, default; `PYAPS_PATCH_WIDTH=static` returns to the lanes planned from the area; `--patch_workers 1` is still the serial code) makes as many lanes as memory and budget allow (7 at 96 GB). After its binning (`ifu_ExGal_prepare` now returns `n_bins`) a patch asks the `WidthBroker` for inner workers: the first patch of every lane wait for each other and share the budget with `fill_widths` (everyone gets 2, then one worker at a time to the patch that would finish last: OB 26037 on 40 CPUs: 606 bins -> 28 workers, ten small patches 2 each; equal patches get equal widths); a patch that starts later takes `min(bins, free workers / lanes without workers)`, at least 2, and waits while fewer than 2 are free. The sum of the widths never exceeds `mp`. A skipped or failed patch tells the barrier it has no work; a lane that dies gives its workers back (run_patches). `run_patches` hands the first patches to the lanes by width so the largest does not land in a narrow lane.
- Tests: `tests/test_ifu_patch_pool.py` +7 (fill_widths, dynamic plan, giant gets the budget and the total never exceeds it, a skipped patch does not block the barrier, a lane that dies gives its workers back).

### Changed (IFU_Gal / IFU_ExGal lane plan: a wide lane for one giant patch, 2026-11-14; aps_ifu_patch_pool.py)
- **Why**: OB 26037 (night 20261112, Imperial): IFU_ExGal had ONE patch of 606 Voronoi bins (1941 s on 24 workers) and ten single stars (84-153 s each, mostly the fixed work of reading and binning the aperture). `plan_workers` only tried lanes of EQUAL width, which slow the giant patch by the same factor as they are narrower, so it chose one lane ("one lane is as fast") and the job took 53 min (3194 s). Estimated wall time of the new plan on the same costs: 24 CPUs `[22, 2]` -20 %, 40 CPUs `[36, 2, 2]` -33 % (the estimate comes from the logged patch times, to be confirmed by a re-run).
- **What**: after the equal-width plans `plan_workers` also tries uneven lane sets (`_best_skewed`: the first lane as wide as pays, the rest even, then single workers moved between lanes while the estimate falls) and takes one only when it is more than `AUTO_TOLERANCE` (5 %) shorter than the best equal plan, so fields of similar patches (OB 16940: 41 patches, 6 lanes of 4) keep their plan. `min_inner` and the memory lane cap still hold. Reason shows as "auto, wide lane for the big patches".
- **Dispatch**: with lanes of different width the shared queue could hand the giant patch to the narrow lane (a race). `run_patches` now gives the first patches, largest first, to the lanes by width (widest lane gets the largest); the rest goes through the queue as before.
- Tests: `tests/test_ifu_patch_pool.py` +4 (giant patch gets a wide lane at 24 and 40 workers, similar patches keep equal lanes, `min_inner` and the cap hold, the widest lane runs the largest patch in 5 runs); the ordering test no longer assumes that all lanes fork at the same instant. Also fixed the stale `--mp_ExGal 24` expectation of the runner test (resources are 40 again). 363 pool tests pass on the Imperial pod environment; the whole suite shows the same 78 golden failures as before this change and no other.

- `aps_ferre.ferre_exe_worker` did not recognise the per-bin control file name `<pixel>.nml<grid>` (it looked for `.nml_`), so a run that ended with exit code 1 and the IEEE underflow note, but had written `<pixel>.opf<grid>`, was printed as "FERRE failed" and left a `.error` file (5175 of each on OB 14699). ### Changed (IFU_Gal and IFU_ExGal process PATCHES side by side inside the CPUs of the job; resources follow, 2026-11-13; doc/SLURM_RESOURCES.md section 13)
- **One driver for both stages**: `py/PyAPS/aps_ifu_patch_pool.py`. The CPU budget `mp` (`--mp_Gal` / `--mp_ExGal`) is split into lanes (a lane = one process that takes patches from a queue and gives each `capacity` inner workers: RVS pool and FERRE bins for IFU_Gal, the PPXF / EMIPPXF / LS pool for IFU_ExGal); the capacities add up to at most `mp`, so there are never more worker processes than CPUs and the pool of a patch is not counted twice. New option `--patch_workers` (script_params `IFU_patch_workers`): `0` / unset = automatic from the patch sizes, `1` = one patch after the other in table order with `mp` workers inside (the old behaviour), `N` = N lanes. With `mp` 1 every setting is the old serial loop, in the same process. Patches start largest first (LPT); the number of lanes is capped by the memory of the job (`SLURM_MEM_PER_NODE` / cgroup / free RAM; 2.5 GB per IFU_Gal lane, 12 GB per IFU_ExGal lane); lines of a patch in a lane start with `[PNNNN] `; the plan is printed.
- **The loop body is a function** (`_run_gal_patch`, `_run_exgal_patch`) that returns `{outcome, fault, proper_drop, ...}`; the parent adds the answers up in table order, so `<head>_<stage>_patches.json`, `IFU_PATCH_SUMMARY` and the exit rules are as before and do not depend on completion order. A failing patch (exception, `sys.exit`, killed worker) does not stop the others.
- **Same results.** IFU_Gal on OB 14699: every column of every product table (`ferre_`, `ferre_spec_`, `rvs_`, `rvsspec_`, `BINSpectra_linear`, `_table`, `_APS`) is identical (difference 0) between the old serial run (-O0 `ferre.x`), the new serial path and the new lanes (mp 8 and mp 10). IFU_ExGal on OB 26140: all columns identical to the production run and to the old code except the `ERR_*` columns of the Monte-Carlo fits (random, as between two runs of the old code). `PYAPS_PATCH_SEED=<n>` seeds numpy with n + patch id per IFU_ExGal patch for comparing runs; lanes start from a fresh random state.
- **Three latent faults of the serial path (`mp_ExGal` 1) of IFU_ExGal**, never taken in production where the pool is always > 1: `IFUExGalPPXF` handed the good pixels returned for one bin to the next bin as its input (every bin started from the pixels the previous one had kept: other results than the pool path, e.g. H3, GOODPIX_PPXF, optimal template of OB 26140 patch 3); `ExGalutil.prettyOutput_Error` did not exist (the EMIPPXF stellar re-fit error handler raised `AttributeError` and failed the patch); and its pPXF bounds were not validated as in the pool path (a start sigma below 25 km/s refused the bin). IFU_ExGal lanes always get at least 2 workers so the pool path is the one that runs; only a stage run with `--mp_ExGal 1` takes the serial path, after the fixes it agrees with the pool path (OB 26140: PPXF identical, EMIPPXF / LS identical for one patch and within 7.5e-4 relative for another; narrowed on 2026-11-14 and settled on 2026-11-15: identical to the pool once the arrays are native, see the entry on byte order below); its EMIPPXF main loop and line-strength branches were not otherwise compared.
- **Resources (`v2`)**: IFU_Gal **10 CPUs** (one ferre.x per grid: 9 grids + 1, as MOS FR asks 9), memory 48 GB (HR the same, was 96), time unchanged; `v2_openmp` IFU_Gal now equals `v2` (OpenMP threads do not help single-object bins); `laptop` IFU_Gal 4 CPUs; IFU_ExGal **40 CPUs / 96 GB (HR 160)** (24 CPUs on 2026-11-13, back to 40 on 2026-11-14: OB 26037, one giant patch, ran 53 min on 24 against 42 on 40; OB 16940, 41 patches, 19 min on 24 against 93 on 40 with the old code) instead of 48 (80) GB; lanes of 12-13 GB share the CPUs the pool of one patch had; `footprint` IFU_Gal 4 + 2 GB per worker (was 8), IFU_ExGal 14 + 0.4 GB. The 2026-11-06 cut to 2 CPUs read the busy cores of the serial code as the size of the job. Measured on the Imperial pod: 62-65 s per bin and worker (-O2 `ferre.x`), PSS 13 GB with 4 lanes and 20 GB with 10 for IFU_Gal, 48.8-51.5 GB for 4 IFU_ExGal lanes.
- **Standalone**: README ("IFU stages on a workstation"), `doc/aps_ifu_Gal.md` 7.7, `tools/check_env.py` warns when `ferre.x` does not link libgomp (the signature of the slow -O0 build).
- Tests: `tests/test_ifu_patch_pool.py` (order, budget arithmetic, memory cap, isolation, aggregation, serial equivalence of both stage functions with fakes), `tests/test_slurm_resources.py`, `tests/test_slurm_machine_checks.py`, `tests/test_check_env.py`.

### Fixed (IFU_Gal ran its FERRE jobs one after the other: OB 14699 of night 20260315 timed out after 24 h with 15 of 44 patches; ferre.x was built without optimisation, 2026-11-13; doc/SLURM_RESOURCES.md)
- **Bins run side by side.** `aps_ifu_ferre.proc_ferre_ifu` handled the spatial bins of a patch one by one and `run_ferre_on_bin` ran the 9 grids of a bin one by one (each a single-thread `ferre.x` of 3-30 s), so the stage used one core of the CPUs it asked for (SLURM's sampled accounting even showed 8-20 %, because processes of 10-30 s fall between its 30 s samples). The work of one bin is now a function (`_one_bin`) and `run_bins` runs `nthreads` (= `--mp_Gal`) of them at the same time, results in the order of the bins; `nthreads` 1 is the old serial loop. A failed bin still only drops that bin.
- **One control file per bin and grid.** `input.nml_<grid>` in the shared work directory is now `<pixel>.nml<grid>` (e.g. `bin0004.nml3`): with bins side by side the old name would have been overwritten while `ferre.x` read it. (The MOS path, `aps_ferre.py`, is unchanged.)
- **Resources.** `v2` asks 4 CPUs / 48 GB (HR 96 GB) for IFU_Gal again (2 / 32 / 64 since 2026-11-06, when the code was serial); `v2_openmp` memory 32 -> 48 GB (HR 96). Re-measure after the first nights.
- **FERRE build.** Upstream commit 60be172 (2026-07-25) changed the makefile to `OPT = -O0` by accident (no optimisation, no OpenMP: `NTHREADS` has no effect); upstream reverted it in be05232 (2026-10-16, reported by Thomas Hajnik). The production pod ran a build of 0e05a6a. `externals/README.md` now says to build upstream f50a006 or later and how to check (`ldd ferre.x | grep gomp`). Measured on one IFU bin (OB 14699, grids 1, 2, 6): output files identical, 18.3 -> 6.5 s, 30.8 -> 10.9 s, 9.4 -> 3.4 s per run (-O2 build, 2.9 times faster).
- Tests: `tests/test_ifu_ferre_parallel_bins.py` (order, overlap, edge cases, unique control files); `tests/test_slurm_resources.py` follows the new request.

### Fixed (line strengths: every index was NaN and the broadening to the LIS resolution never ran, OB 26133, 2026-11-06; doc/aps_ifu_ExGal.md section 17)
- **`lsindex_spec.sum_counts` returned a 1-element array** when a band edge falls inside a pixel (always, for real bands); on NumPy 2.5 `index[k] = index0[0]` then raised `setting an array element with a sequence`, `run_ls` caught it (`lsindex measurement failed`) and wrote NaN. Result on OB 26133 (IFU_ExGal, 4 patches, and the MOS LS product): **0 finite values out of ~59,000 index and error cells**. Fix: the fractional-pixel terms are summed to a scalar. Test: `tests/test_lsindex_scalar.py`.
- **`gaussian_filter1d() got an unexpected keyword argument 'truncate'`** (hundreds of WARNINGs per IFU_ExGal / MOS LS run; 14 in OB 26133 IFU_ExGal, about half of the 553 MOS bins): `IFUExGalLS.py` and `MOSExGalLS.py` called `ppxf.ppxf_util.gaussian_filter1d(spec, sigma, truncate=, mode=)`; that pPXF function (same signature in pPXF 9.5.0 on both pods, and in every pPXF version) is `(spec, sig)`, a deprecated per-pixel-sigma convolution, and takes neither argument. The `TypeError` was caught, a WARNING printed and the spectrum was kept **unbroadened** (FWHM_FLAG = 3), so the line-strength indices of every bin that needed broadening were measured at the original resolution, not at the LIS 8.4 A system. New `py/PyAPS/aps_ls_broaden.py` (`broaden_variable_sigma`, NumPy only, +-4 sigma kernel of the local width, edge pixel continued; independent of the pPXF and SciPy versions) replaces the call in both modules. The former 3 / 2 sigma "adaptive truncate" tiers for wide kernels (they were never executed) are not carried over: they would have narrowed the Gaussian by up to 12 %. Tests: `tests/test_ls_broaden.py` (matches scipy for a constant sigma, FWHM follows sigma per pixel, NaN stays local, both modules call the helper with arguments it accepts). Doc: `doc/aps_ifu_ExGal.md` (FWHM_FLAG table).
- **Width of the extra Gaussian was computed for the wrong pixel grid** (found while testing the fix above; separate commit): `sigma = FWHM_dif / wave * c / 2.355 / velscale` is in pixels of the LOG grid, but the spectra are rebinned to a LINEAR grid (`log_unbinning`) before the broadening. On the OB 26133 grid (0.3356 A/pixel, 24.4 km/s log step) the width was right only at 4122 A, 18 % too small at 5000 A, 31 % too small at 6000 A and 37 % too large at 3000 A, i.e. a 3 A line broadened 'to 8.4 A' came out at 6.9 A at 5200 A and 6.2 A at 6000 A (10.2 A at 3300 A), so the Lick region was left narrower than the LIS system. New `fwhm_to_sigma_pixels(FWHM, wave)` (local pixel step, valid for linear and log grids) in both modules. Effect on 9 bins of OB 26133 patch P0010 (LSF taken as 2.6 A, sigma_v 143 km/s): Mgb 0.47 A, NaD 0.61 A, Fe5335 0.37 A, Fe4383 0.12 A, Fe5270 0.13 A different from the log-grid formula; against the unbroadened spectra (what flag 3 products contain) Mgb -1.7, Fe5270 -1.0, Fe5335 -1.1, NaD +2.2, Hbeta +0.4, HdeltaA -1.2, HgammaA +1.4 A. Tests in `tests/test_ls_broaden.py`.

### Added (the resource checks know the machine: probe, sites, limits policy; depth-first order of the jobs)
- **Machine probe** (`py/PyAPS/aps_resource_probe.py`, standard library only): a SLURM cluster (version, plugins, partitions, every node's CPUs / `RealMemory` / allocation / state; `scontrol` with `sinfo` as the fallback, 5 s per command, a hung controller is tried once) or this machine (CPUs with `sched_getaffinity` and the cgroup v1/v2 quota, RAM with `/proc/meminfo` and the cgroup limit, swap, load, Linux / WSL / macOS, container) and whether `ferre.x` links OpenMP. Every failure is "unknown" with a message, never an exception; the answer is cached for a minute.
- **Limits policy** `limits: off | warn | clamp | error` (new: `error`), chosen by `--slurm_limits`, `PYAPS_SLURM_LIMITS`, script_params `slurm_limits`, the site, the profile. `warn` (the default of every production profile) prints the request that does not fit with the value and the `--slurm_set` that would fit and **keeps** it; `clamp` lowers only what does not fit; `error` refuses before anything is submitted, only when the request can never run (the 380 GB FERRE request on a 351 GB node), listing every stage and the alternative. A request that fits is never changed. The check compares CPUs and memory against the same node (no node with 40 CPUs and 300 GB together is also a finding).
- **Sites**: the table's `sites:` now describes a place (`match`, `profile`, `profile_openmp`, `ferre_openmp`, `limits`, `mem_fraction`, `cpu_fraction`, `expect`; the old `max_*` pins still work for a named site). Generic sites `local` and `slurm` are in the table; an installation lists its own in `slurm_sites.yaml` (`PYAPS_SLURM_SITES_FILE`, `slurm_sites_file`, or `PyAPS_CONFIG`). The site is detected from the machine or named (`--slurm_site`, `PYAPS_SLURM_SITE`, `slurm_site`); the word `site` as profile (`--slurm_profile site`) takes the site's profile (nothing chooses it by itself, so no profile changes). New profile `laptop`.
- **Machines without SLURM** (a bash run, `--hpc 1`): the CPUs are a share (`cpu_fraction`) of what the process may use and the RAM a share (`mem_fraction`) of what is available, both divided by `--parallel_jobs`; a stage whose workers do not fit in the RAM runs with fewer workers (table section `footprint`, measured PSS per stage). Default policy of the `local` site: `clamp`.
- **Operator commands**: `python -m PyAPS.aps_slurm_resources probe|site|check` (read only; `check` exits 0 / 1 / 3; `--machine-file` previews another machine).
- **Recorded**: `slurm_resources_effective.json` gets `environment`, per stage `requested`, `adjustments`, `fits`, `footprint_gb`, `limits_policy`, `nice`, `comment`, and the run's `priority`; every stage log starts with a `PyAPS machine check:` line.
- **Depth-first order of the jobs** (table section `priority`; policy `depth_first`, **off in every profile**: in the private experiments of 2026-11-05 the nice offsets did not change the order, see `doc/SLURM_RESOURCES.md` section 10): every job gets a non-negative `--nice` (class base + 800 x stages still to come + 100 x pair index) and `--comment pyaps:<uapsid>:p<pair>:<class>:<STAGE>`, so the first pair of a night completes first (the queue is FIFO by eligible time and the late stages of the first pair used to queue behind the first stages of every later pair). Classes `scheduled` (4500) and `offline` (no nice at all: it rises above the queue's floor of 1 with its age and passes the scheduled jobs that sit at the floor): a run someone waits for is ahead of the daemon's jobs. `--slurm_priority`, `--priority_class`, `--pair_index` (env `PYAPS_SLURM_PRIORITY`, `PYAPS_PRIORITY_CLASS`, `PYAPS_PAIR_INDEX`). An escalation retry keeps the pair index of its chain. Bounded below 10000, nothing starves. Doc: `doc/SLURM_RESOURCES.md`, sections 9 and 10.
- Tests: `tests/test_resource_probe.py`, `tests/test_slurm_machine_checks.py` (fake clusters, a laptop, a container with cgroup limits, a hung `scontrol`, garbage output; no ordinary run on a production-like fake cluster is blocked or changed); the golden tests of the `default` profile are unchanged.
- Changed: with no look possible (no SLURM, no probe) nothing is checked; the old `limits` argument of `resolve()` and the `sites` pins behave as before; `resolve()` returns a dict that also carries `.environment` and `.priority`.

### Added (SLURM resources: one table, memory requests, thread consistency)
- **One table for the CPUs, memory and time limit of every job** (`configs/slurm_resources.yaml`, `py/PyAPS/aps_slurm_resources.py`, `doc/SLURM_RESOURCES.md`). - Escalation record (`slurm_resources_escalation.json` beside the scripts, written by the operations layer): a stage that ended OUT_OF_MEMORY or TIMEOUT is generated again once with 1.5 x its memory / time limit (never beyond the largest node or the partition limit).
- **FERRE threads match the CPUs of the stage** (`aps_ferre.ferre_threads_per_process`): the stage runs one `ferre.x` per grid at the same time and wrote `NTHREADS = --mp` into each `input.nml`, i.e. 9 grids x 18 threads on 18 CPUs; each process now gets `max(1, mp // min(mp, grids))` threads (`PYAPS_FERRE_THREADS=mp` restores the old value, a number sets it). A `ferre.x` built without OpenMP ignores `NTHREADS`: no change for it.
- The effective values and the escalation record are kept per run (the uapsid, `<uapsid>:CS` for the CS chain) in the scripts folder of the OB, which holds the scripts of every pair of the OB. The runner looks for `slurm_resources.yaml` in the `PyAPS_CONFIG` folder of its script_params first, then in its own checkout (`slurm_resources_file` / `PYAPS_SLURM_RESOURCES_FILE` name another).
- `aps_job_report.py` also reports a job that SLURM killed for exceeding its memory request but listed as FAILED (the job's own script is killed with it and writes no line); it reads the `.err` file.

- Redrock per-arm chi2 modification (`aps_rr.py`): per-camera archetype columns are solved on, and averaged over, the arms in which they are non-zero (the stored Legendre coefficients were diluted by 1/n_arm; reported chi2 and rankings were unaffected); an arm to which the template does not contribute now adds its weighted flux squared to the chi2, as in the upstream joint fit, instead of discarding the trial redshift.
- `tests/test_aps_common_args.py` reads only the option lines of `--help`, skips scripts whose optional dependencies are missing, and lists the flags added since the original snapshot.

### Added
- `--rr_solver perarm|joint` (default `perarm`, unchanged behaviour) to select the per-arm or the upstream joint multi-arm solve; `tests/test_rr_perarm_patch.py` (synthetic tests, including the scope of the modification).

### Fixed (static plot images can no longer hang a job)
- Eleven L2 jobs (PPXF, EMI, RR, FR, RVS) of two APS hosts stopped at the plotting step in October 2026 and ran into the 2-day SLURM limit: `fig.write_image()` renders through Kaleido 1.x, which drives a headless Chrome and waits for it without a deadline while it starts, navigates and closes (only the render itself has the 90 s limit). In the hung jobs Chrome was alive and idle, Python was waiting for it, no CPU was used, and the night stayed PROCESSING because the runner saw failed jobs for two days. A diagnostic picture must never cost a night.
- New `PyAPS.apsPlot.export.write_image(fig, path, scale=...)` replaces every `fig.write_image(...)` of the pipeline (a test enforces it). It renders in a separate worker process (`apsPlot/_export_worker.py`, its own session, one browser for many images, so also about ten times faster than a browser per image); each image has a deadline (`PYAPS_PLOT_TIMEOUT`, default 120 s; first image `PYAPS_PLOT_START_TIMEOUT`, 180 s); on timeout the worker's stack and the last lines of its log are written to the job log, worker and browser are killed, the picture is skipped and the next one starts a new worker; after `PYAPS_PLOT_MAX_FAILURES` (3) timeouts in a row the pictures of the process are switched off; the worker is replaced every `PYAPS_PLOT_RECYCLE` (200) images. It returns False instead of raising, so a figure never stops a data product. `PYAPS_PLOT_EXPORT=inprocess` restores the plain call (no deadline), `off` writes no static image. Files are written under a temporary name and renamed, so a killed render leaves no truncated picture. `tests/test_plot_export.py` (fake worker: hang, death, errors, fork safety; an opt-in test with the real Kaleido: `PYAPS_TEST_KALEIDO=1`).
- Every L2 SLURM job now has a `--time` limit sized from the jobs that completed (`aps_runner.DEFAULT_SLURM_TIME`: RR/FR/PPXF 8 h, EMI 6 h, RVS/LS/L2merge 2 h, IFU stages 18 h; the longest completed job of each kind is at most half of it), so a job that waits for ever dies in hours instead of 2 days. Override one stage with the `script_params` key `slurm_time_<STAGE>` (quoted, e.g. `'12:00:00'`) or switch it off with `'None'`. The CS stages have no limit. `tests/test_slurm_time_limits.py`.

### Fixed (aperture convention)
- Aperture definition made consistent and documented. `A_world`/`B_world` (patch tables), the `area`/`mask_areas`
  entries and `make_patch_array(a_arcsec, b_arcsec)` are FULL axis lengths (diameters), the `width`/`height` of the
  extraction ellipse, as the Gaia mask rows, the SEP rows and the MOS circular selection already assumed. Docs and
  labels that called them semi-axes (`doc/aps_ifu_prepare.md`, the IFU tutorial, the cube preview
  printout, the `make_patch_array` docstrings) now say full axis. A single helper, `aps_utils.aperture_sky_region`,
  builds the region and is covered by aperture-boundary tests (`tests/test_aperture_convention.py`).
  **No numerical behaviour changed**: patch-table products are unaffected; `make_patch_array(10, 6)` has always
  extracted within 5" and 3" of the centre, and the seg3d merged-target aperture setting
  (`seg3d_merge_aperture_arcsec`, default 2.0) has always been a diameter (1.0" extraction radius). Past L2 products
  therefore need no reprocessing; read those numbers as diameters.

### Fixed (interactive mask tool)
- `aps_ifu_utils.add_mask_region` (the `mask <ra> <dec> <radius_arcsec>` command of the patch-table editor) stored the
  typed radius as the full axis length, so the masked radius was half of what was typed. It now stores the diameter, like
  the Gaia mask rows, so the typed radius is the real masked radius. Only mask rows added by hand with that command are
  affected: they masked half the intended radius.

### Added (Galactic aperture factor)
- `gal_aperture_factor` (CLI `--gal_aperture_factor`) for the Galactic IFU route: an explicit factor applied to both
  full aperture axis lengths. The default (`None`) keeps the old behaviour, 0.5 for patch-file rows and 1.0 for a
  `patch_array`, so existing results are unchanged; set a number to make both routes select the same spaxels.

### Documentation
- `doc/aps_rr.md` states where the per-arm solve is active (coarse scan and per-camera archetype solve; Redrock's fine scan keeps the joint solver), what the returned coefficients mean, and removes the unsupported claims of independence from IVAR scaling and of removing a joint-fit bias.

### Documentation (README)

  Added to `CITATION.cff` and the README (badge, citation block, BibTeX).

### Added

  extras `[pipeline]`, `[cs]`, `[server]`, `[performance]`, `[dev]`, `[docs]`) and a table of exactly

  `PyAPS` namespace through the `pyaps.extensions` entry point. Nothing changes when none is installed.
